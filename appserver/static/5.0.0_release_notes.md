## Overview

4.1.1 was a deterministic Active Directory auditing app: threshold rules, critical-object lists, and a
continuously maintained KV Store inventory of users, groups, computers, OUs, GPOs and domains built from
`admon` data.

5.0.0 keeps every one of those detections exactly as they are and layers four new capabilities on top of the
existing entity inventory:

1. **MITRE ATT&CK mapping** of the shipped detection content.
2. **Feature engineering** — stable daily behavioural features written to a summary index.
3. **Three behavioural risk models** plus model operations, writing scored entities into a new KV Store risk
   collection.
4. **An optional GenAI/LLM narrative layer**, and **a labeled evaluation harness** that measures the models.

> **Everything new in this release ships disabled.** A 4.1.1 install upgraded to 5.0.0 behaves identically to
> 4.1.1 until an administrator explicitly enables the new content. There is no silent change in alerting
> behaviour, no new scheduled load, and no network egress.

## What's New

### 1. MITRE ATT&CK mapping (Phase 0)

Detection content is now mapped to ATT&CK techniques so it can be reasoned about alongside the rest of a
security program.

- `lookups/ms_ad_obj_mitre_map.csv` — 146 rows, one per saved search: **81 mapped to real ATT&CK techniques,
  65 deliberately marked `N/A`** (operational/reporting searches that are not detections). Multi-technique
  cells are `|` delimited.
- Twenty detection searches additionally carry `action.correlationsearch.annotations` JSON, so they surface
  correctly in an Enterprise Security-style workflow.
- The mapping is applied at search time by the `ms_ad_obj_mitre_enrich` macro rather than baked into each
  search, so re-mapping a technique is a one-lookup edit.

### 2. ML feature engineering (Phase 0)

Models are trained on stable, versioned features rather than raw events. Four scheduled searches write daily
feature rows to a summary index, each tagged with a `feature_set` marker.

| Feature set | Grain | What it captures |
|---|---|---|
| `entity_change_velocity` | admin/service account × day | AD object change counts, action and object-type breakdown, off-hours ratio, target/host spread |
| `logon_type_vector` | account × day | Fixed-width authentication vector by EventCode (4624/4625/4768/4771/4776) and by resolved `Logon_Type` |
| `admin_session_features` | admin × day | Session counts, source/destination host spread, active span, off-hours ratio |
| `group_membership_delta` | group × day | Membership adds/removes/net delta split by group scope (global, domain-local, universal) |

The schemas are deliberately fixed-width so that peer models never see column drift.

### 3. Three behavioural risk models and model ops (Phase 1)

All model output lands in one place — the `AD_Obj_Risk` KV Store lookup — carrying a MITRE technique id, so
model-driven risk routes through the same severity and critical-object workflow the app already had.

| Model | Algorithm | Risk type written | ATT&CK | MLTK required |
|---|---|---|---|---|
| `ad_obj_change_velocity_df` | MLTK `DensityFunction` per account | `change_velocity` | T1098 | Yes |
| `ad_obj_peer_kmeans` | MLTK `KMeans` (k=8) + SPL z-score deviation | `peer_logon_deviation` | T1078.002 | Yes |
| `ad_obj_privpath_spl` | Pure SPL group-nesting graph walk | `priv_path_change` | T1484 / T1098 | **No** |

- **Change velocity** catches the admin who normally makes 3 changes a day making 300. `risk_score` is
  `1/(1+ProbabilityDensity)`, so a vanishing probability density scores near 1.0.
- **Peer group** clusters accounts on scale-invariant authentication *ratios* (plus two OU-structure features
  used for clustering only), then measures each account's Euclidean z-score distance from its own cluster.
  MLTK KMeans emits no distance-to-centroid, so the deviation is computed in SPL. Clusters smaller than five
  members are skipped as statistically meaningless.
- **Privilege path** seeds on critical / `adminCount=1` / `isCriticalSystemObject` groups and walks the
  `member` attribute four nesting levels down, reducing to minimum depth and critical-group reach per entity.
  It classifies each entity as `new_reach`, `depth_decreased`, `reach_increased` or `unchanged`, promotes a
  staging lookup to the baseline, and only then writes the changed rows. This is the detection that catches a
  distribution list quietly nested under a Tier-0 group.
- **Model ops**: weekly re-fit, daily apply, 90-day risk retention, and a week-over-week drift check that
  flags a >3× move in outlier rate in either direction (a large increase usually means a stale model; a large
  decrease usually means the feature searches or the fit stopped running).

Model output rows are upserted on a deterministic `_key` of
`<risk_type>:<entity_type>:<entity>:<scored_day>`, so a re-run corrects rather than duplicates.

### 4. GenAI / LLM layer — optional, disabled by default (Phase 2)

The app's first `bin/` directory adds three **read-only, descriptive** custom search commands. They add fields
to rows already in the pipeline; they never write to an index, a lookup, or the KV Store, and they never
execute anything.

- `| adexplain` — plain-English narrative for an AD entity: decoded `userAccountControl` bitmap, group nesting
  chain, recent change summary. Grounded only on KV Store fields passed in the prompt.
- `| adtriage` — who / what / when / blast-radius paragraph for an `AD_Obj_Risk` row, always shown beside the
  underlying model values.
- `| adnl2spl` — natural language to **suggested** SPL, grounded on this app's own macro/lookup vocabulary.
  The SPL is returned as a **string field for human review and is never executed by this app**.

**The template-fallback guarantee:** with `ad_obj_ai.conf` at its shipped `enabled = 0, provider = none`, every
one of these commands produces a deterministic, rule-based narrative and stamps `ai_status = template`. That is
a fully supported operating state, not a degraded one. No model is contacted, no endpoint is implied, and
nothing leaves the instance.

### 5. Evaluation harness (Phase 3)

LLM and ML features regress silently without one.

- `lookups/ms_ad_obj_ml_evalset.csv` — a labeled ground-truth eval set: **32 scenarios, 17 that should be
  detected and 15 that should not**, spanning all three risk types. Columns: `scenario_id`, `scenario_name`,
  `entity`, `entity_type`, `domain`, `risk_type`, `expected_detection`, `mitre_technique_id`, `severity`,
  `notes`.
- It is the AD-side consumer of the `batch_data_eventgen` labeled-corpus ground-truth manifest; `scenario_id`
  is the contract between the two.
- `AD_Obj_ML_Eval_Score` computes per-`risk_type` true positives, false positives, false negatives, true
  negatives, **precision, recall and F1**, and writes them to the summary index tagged
  `feature_set = model_eval_scores` so scores can be trended release over release.
- Two **Model Evaluation** panels on the ML Risk Overview dashboard show the same scores plus the FP/FN detail
  rows, including each scenario's `notes` explaining what it was designed to test.

## Requirements and dependencies

| Requirement | Version | Required for |
|---|---|---|
| Splunk Enterprise / Splunk Cloud | 9.2+ | The app. Python 3 runtime and `splunklib` for the GenAI commands. |
| Splunk Add-on for Microsoft Windows | 4+ | **The whole app** — unchanged, longstanding requirement. This is the data source. |
| Splunk Machine Learning Toolkit (MLTK) | **5.4+** | The change-velocity and peer-group models only |
| Splunk App for Data Science and Deep Learning (DSDL) | 5.2+ | **Optional.** Only if you choose `provider = local_dsdl` for the AI layer |

Notes:

- MLTK is declared in `app.manifest` as `"Splunk_ML_Toolkit": {"version": "5.4+", "optional": true}`. It is
  marked **optional** because it is accurate: with the ML searches at their shipped `disabled = 1`, the app
  installs and runs completely without MLTK. Enabling `AD_Obj_ML_ChangeVelocity_*` or `AD_Obj_ML_PeerGroup_*`
  without it will fail at the `fit`/`apply` command.
- **The privilege-path model and the evaluation search require no MLTK at all** — they are pure SPL over the
  KV Store and lookups.
- **AI features are entirely optional and off by default.** DSDL is not required by anything that ships
  enabled, and is not declared as a dependency.
- The KV Store collections and the `local = true` search commands mean this app belongs on search heads.

## Security notes

The GenAI layer was built fail-closed. Every gate below is enforced in `bin/ad_obj_llm_lib.py`, not in
documentation.

- **Capability gating.** Every command calls `require_capability()` for `ad_obj_can_use_ai` before doing any
  work, and denies both on absence of the capability *and* on inability to verify it — an unverifiable
  identity is a denied identity. Out of the box only `admin` holds the capability; a purpose-built
  `ad_obj_ai_user` role is provided for analyst teams.
- **Secrets via `storage/passwords` only.** The credential is read at search time from Splunk's encrypted
  store using the search's own session key. There is deliberately **no `.conf` setting that accepts a
  credential**, no environment-variable fallback, and no disk cache. The retrieved value builds one
  `Authorization` header and is never logged, never returned in a field, and never written to the audit
  record.
- **Fail-closed by design.** Disabled, misconfigured, timed out, unreachable, or schema-invalid — every one of
  those paths returns the deterministic template narrative rather than degraded or partial model output.
  When auditing is enabled and the audit log cannot be opened, the model call is **refused** rather than run
  unaudited.
- **No auto-execution of generated SPL.** `adnl2spl` returns SPL as a string field for human review. Nothing
  in `bin/` uses `eval()`, `exec()`, `subprocess`, `os.system`, or a shell, and no model output is placed
  anywhere Splunk would execute it.
- **Grounding-field allowlist.** `allowed_grounding_fields` in `ad_obj_ai.conf` is the complete list of what
  may reach a prompt. A field not named there never reaches one. `_raw`, `_time` and other Splunk internals
  are on an additional hard deny list the setting cannot override. Surviving values are normalised, stripped
  of control characters, scanned for credential-shaped content (API keys, bearer tokens, JWTs, PEM private
  keys, long hex blobs) which is masked, screened for prompt-injection phrasing which is removed, and capped
  by a character budget.
- **Structured output contract.** Every response must be a single JSON object matching a declared schema.
  Prose is never scraped for JSON, partial objects are never salvaged, and raw model text is never passed
  through.
- **Audit logging.** One JSON record per invocation to
  `$SPLUNK_HOME/var/log/splunk/ad_obj_llm_audit.log`: user, command, provider, model, prompt **SHA-256**,
  prompt character count, token counts when reported, latency, outcome, and the *names* of the grounding
  fields used. **Never recorded:** the prompt text, the response text, any grounding value, or any
  credential.

## Upgrade instructions (from 4.1.1)

1. **Back up** as you would for any app upgrade, then install 5.0.0 over 4.1.1 in the usual way. Restart or
   reload as your deployment requires. `local/` customisations are untouched.
2. **Verify the baseline.** Nothing needs to be done for the app to keep behaving exactly as 4.1.1 did. All
   thirteen new searches ship `disabled = 1`; `ad_obj_ai.conf` ships `enabled = 0, provider = none`.
3. **Enable in this order** — each step depends on the previous one having produced data:

   | # | Step | Notes |
   |---|---|---|
   | 1 | Install MLTK 5.4+ on the search head that will run the scheduled searches | Skip only if you intend to use privilege-path analytics alone |
   | 2 | Enable the four `AD Objects - ML Feature - *` searches | Confirm rows land: `index=summary feature_set=entity_change_velocity \| stats count by date_day` |
   | 3 | Accrue **30 days** of feature rows, or backfill by running each feature search over a historical window | **Do not skip.** A fit over a few days of data flags almost everything |
   | 4 | Enable and run `AD_Obj_ML_ChangeVelocity_Fit` and `AD_Obj_ML_PeerGroup_Fit` once | Verify on the *Model Artifacts* dashboard panel before continuing |
   | 5 | Enable the applies, then `AD_Obj_ML_PrivPath_Update` and `AD_Obj_ML_PrivPath_Alert` | The first PrivPath cycle only seeds the baseline and writes no risk rows |
   | 6 | Enable `AD_Obj_ML_Risk_Retention` and `AD_Obj_ML_Drift_Check` | Weekly model ops |
   | 7 | Enable `AD_Obj_ML_Eval_Score` **last**, and only against a labeled corpus | On live data it reports large meaningless `false_positives_unlabeled` counts |
   | 8 | (Optional, independent) Configure the AI layer in `local/ad_obj_ai.conf` | Grant `ad_obj_can_use_ai` and store the credential in `storage/passwords` first |

4. **Summary index.** The feature searches write to the literal index `summary`. `action.summary_index._name`
   cannot take a macro, so if you repoint it you must change **both** the `_name` value in each stanza *and*
   the `ms_ad_obj_ml_summary_index` macro.

## Known limitations / not yet validated

Stated plainly, because a release note that hides these is worse than useless.

- **The models are untuned against production Active Directory data.** They ship as baselines with defensible
  defaults. **There is no production-validated false-positive rate for any of the three models**, and any
  number quoted without your own eval run would be invented. The evaluation harness is how you measure yours.
- **No live-model smoke test has been performed.** A real MLTK `fit` followed by a real `apply` against real
  directory data has not been executed as part of this release. The SPL is reviewed, not runtime-proven.
- **`k = 8` for the peer-group model is not empirically tuned** for any particular estate. A very homogeneous
  directory will over-cluster and produce noise; a very heterogeneous one will under-cluster and miss
  deviations. Inspect the cluster sizes emitted by `AD_Obj_ML_PeerGroup_Fit` before judging the detections.
- **Change-velocity threshold semantics.** `ms_ad_obj_risk_threshold = 0.01` is a *tail probability*. Roughly
  1% of scored account-days fall outside the fitted distribution **by construction** — that is the definition
  of the setting, not a measured error rate. Recurring batch patterns (quarter-end provisioning, mass
  onboarding, DC promotions, migrations) are the dominant real false-positive source.
- **Privilege-path cold start.** The first run against an empty baseline writes **zero** risk rows and only
  seeds `ms_ad_obj_privpath` — by design. Expect a burst on the first run after any large migration, and note
  that every *approved* addition to a Tier-0 group is a true `new_reach` and will be reported.
- **Nesting depth is fixed at four levels.** A privilege path deeper than four hops is not seen.
- **`splunklib` dependency.** The GenAI commands are Splunk SDK chunked (v2) commands and require `splunklib`.
  Splunk Enterprise 9.2+ provides it; on an older or unusual runtime, drop the Splunk Python SDK into
  `bin/lib/` and it is picked up automatically.
- **Per-row LLM cost.** `adexplain`, `adtriage` and `adnl2spl` are per-row commands. Put `| head` in front of
  them on large result sets; the shipped dashboard panels already cap themselves at 10 rows.
- **SimpleXML quote-escaping wart.** The AI Assistant dashboard passes your question into SPL through a token,
  so double quotes in a question are not supported — they produce a search parse error. Rephrase without them.
- **Eval search subsearch limits.** `AD_Obj_ML_Eval_Score` reads `AD_Obj_Risk` through an `append` subsearch,
  so on a very large risk collection it is subject to the standard subsearch result and time limits.
- **Eval scores are only meaningful on a labeled corpus replay.** On live production data the unlabeled
  entities dominate and `precision_incl_unlabeled` should be ignored.

## Rollback procedure

Returns the app to 4.1.1 behaviour without uninstalling it.

1. **Disable the searches.** *Settings → Searches, reports and alerts*, filter on the `ms_windows_ad_objects`
   app, and disable every search named `AD_Obj_ML_*` and `AD Objects - ML Feature - *`. That alone stops all
   model activity immediately — nothing else in the app calls a model.
2. **Turn off the AI layer** if it was enabled: set `enabled = 0` and `provider = none` in
   `local/ad_obj_ai.conf`. Every AI surface reverts to the deterministic template path. To remove access
   entirely, delete the `ad_obj_can_use_ai` grant from your roles.
3. **Remove the fitted models:**

   ```
   | deletemodel ad_obj_change_velocity_df
   | deletemodel ad_obj_peer_kmeans
   ```

   Or delete the `__mlspl_ad_obj_*.mlmodel` lookup table files from *Settings → Lookups → Lookup table files*
   in this app.
4. **Clear the risk collection:**

   ```
   | inputlookup AD_Obj_Risk | where 1=0 | outputlookup key_field=_key AD_Obj_Risk
   ```

   Or drop it wholesale:
   `DELETE /servicesNS/nobody/ms_windows_ad_objects/storage/collections/data/AD_Obj_Risk_kv`
5. **Clear the privilege-path baseline** for a clean re-seed later: empty `lookups/ms_ad_obj_privpath.csv` and
   `lookups/ms_ad_obj_privpath_new.csv` down to their header rows.
6. **Optional — remove accumulated feature rows** from the summary index
   (`feature_set` in `entity_change_velocity`, `logon_type_vector`, `admin_session_features`,
   `group_membership_delta`, `model_eval_scores`) using your normal index-cleanup process.
7. Nothing above touches the `AD_Obj_*` inventory collections, the deterministic saved searches, or any
   existing dashboard. The MITRE annotations are metadata only and are safe to leave in place.
